# ADR-003: Выбор слоя персистентности

**Статус:** Принято  
**Дата:** 2026-04-04  
**Контекст:** Engineer Challenge — модуль аутентификации, деплой в Kubernetes

---

## Решение

**KV-хранилище Dragonfly** как единственный слой персистентности для `User` и `PasswordResetToken`

---

## Контекст и постановка проблемы

Приложение деплоится в Kubernetes с двумя репликами (`replicas: 2`). Изначально все репозитории использовали `InMemory` реализации на основе `ConcurrentHashMap`. При горизонтальном масштабировании это приводит к split-brain: пользователь, зарегистрированный на pod-1, недоступен на pod-2.

Требуется shared state между подами при минимальной сложности инфраструктуры.

Рассматривались три класса хранилищ: **KV** (Dragonfly), **SQL** (PostgreSQL), **Document NoSQL** (MongoDB).

---

## Рассмотренные варианты

### Dragonfly (выбран)

Redis-совместимое KV-хранилище с многопоточной архитектурой.

**Плюсы:**
- Один компонент закрывает оба use case: персистентность пользователей (HASH) и TTL-токены (STRING + EXPIRE)
- Нет необходимости в PersistentVolume / PVC в Kubernetes
- Нативный TTL — `PasswordResetToken` истекает автоматически без cron
- Легковесный: минимальное потребление RAM и CPU
- Многопоточная архитектура — Dragonfly превосходит однопоточный Redis по производительности
- Работает с существующим Lettuce-клиентом без изменений кода

**Минусы:**
- `findByEmail` реализован через вторичный индекс вручную (`user:email:{email} → uuid`) — нет нативных запросов по полям
- Атомарность HSET + SET индекса требует MULTI/EXEC для строгих гарантий
- Персистентность по умолчанию отсутствует — требует `--save` или AOF

**Снижение рисков:**  
Домен прост : `User` и `PasswordResetToken` без сложных связей и запросов. Рассинхронизация индекса некритична для данного челленджа.

---

### PostgreSQL (отклонён)

Классическая реляционная БД с полным SQL, индексами и ACID-транзакциями.

**Плюсы:**
- `findByEmail` — простой `WHERE email = ?` с индексом
- Полные ACID-гарантии для всех операций
- Надёжная персистентность
- Привычная для большинства команд

**Причины отклонения:**
- Требует PersistentVolume + PVC в Kubernetes — усложняет деплой
- Отдельный StatefulSet, миграции схемы (Flyway/Liquibase)
- TTL для `PasswordResetToken` требует cron или фоновой задачи очистки
- Тяжелее по RAM/CPU для одного пода Dragonfly

---

### MongoDB (отклонёна)

Документо-ориентированная БД с гибкой схемой и богатым языком запросов.

**Плюсы:**
- `findByEmail` — нативный `{ email: "..." }` с индексом, вторичный индекс не нужен
- `User` естественно ложится в документ без маппинга на таблицы
- ACID-транзакции с версии 4.0
- TTL index — `PasswordResetToken` можно удалять автоматически через TTL index
- Гибкая схема — хорошо адаптируется если `User` усложнится в будущем

**Причины отклонения:**
- Требует PersistentVolume + PVC в Kubernetes — статус StatefulSet и дисковое хранение избежать не удастся, противоречит цели минимизации компонентов
- TTL index в MongoDB — не мгновенный: фоновый процесс удаляет документы раз в 60 секунд, в отличие от мгновенного EXPIRE в KV
- Избыточно для домена: гибкая схема не даёт преимуществ при фиксированной структуре `User`
- Тяжелее по RAM чем Dragonfly
- Дополнительные зависимости: нужен Mongo Kotlin driver — ещё один компонент в проекте

---

## Схема ключей Dragonfly

| Ключ | Тип | Содержимое | TTL |
|---|---|---|---|
| `user:{uuid}` | HASH | все поля `User` | нет |
| `user:email:{email}` | STRING | uuid | нет |
| `reset:{token}` | STRING | `userId\|expiresAt` | да |
| `user-token:{userId}` | STRING | token | да |

---

## Последствия

- `InMemoryUserRepository` и `InMemoryPasswordResetTokenRepository` сохраняются для локальной разработки без Docker (`STORAGE_BACKEND=memory`)
- Переключение через `STORAGE_BACKEND` — без изменения кода
- Если домен усложнится (появятся JOIN, агрегации) — PostgreSQL становится предпочтительным направлением эволюции
- В production-деплое — включить Dragonfly `--save` или использовать managed Redis-совместимый сервис
- При необходимости строгих гарантий записи — обернуть `save` в MULTI/EXEC
