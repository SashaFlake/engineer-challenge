# ADR-005: Стратегия Rate Limiting

**Статус:** Принято  
**Дата:** 2026-04-05  
**Контекст:** Engineer Challenge — модуль аутентификации, деплой в Kubernetes (ADR-001, ADR-002, ADR-003)

---

## Решение

**Два слоя rate limiting:**

1. **Nginx** — грубый edge-лимит по IP, защита от флуда. Реализовано.
2. **Dragonfly** (ADR-004) — точные лимиты по email/операции на уровне приложения, защита от брутфорса. Запланировано.

Слои независимы: Nginx не мешает реализовать Dragonfly-лимиты позже.

---

## Контекст и постановка проблемы

ГрафQL-сервис имеет единственный публичный эндпоинт `POST /graphql` (ADR-002). Единый эндпоинт исключает нативный rate limiting по URL — это принятая стоимость выбора GraphQL.

Уязвимости:
- **DDoS / флуд** — множество запросов с целью перегрузки JVM
- **Брутфорс паролей** — перебор пароля конкретного аккаунта, в том числе с разных IP
- **Credential stuffing** — массовая проверка утёкших пар login/password

Сервис деплоится в 2+ реплики (Kubernetes HPA).

---

## Рассмотренные варианты

### Nginx `limit_req` (реализован)

`limit_req_zone` по `$binary_remote_addr`: 20 req/s, burst 10.

| | |
|---|---|
| Защищает от | Флуд / DDoS по IP |
| Не защищает от | Брутфорса с разных IP по одному email |
| Код в приложении | Нет |
| Порт приложения снаружи | Закрыт |
| Корректность при scaling nginx | Счётчики не шарятся между репликами |
| Новый компонент в стеке | Да |

### Dragonfly distributed counters (запланировано)

`INCR rate:{op}:{email}` + `EXPIRE` на уровне приложения. Dragonfly уже в стеке (ADR-004).

| | |
|---|---|
| Защищает от | Брутфорса по email с любых IP |
| Корректность при scaling | Да — счётчики шарятся между всеми репликами |
| Новый компонент | Нет (Dragonfly уже есть) |
| Код в приложении | Да |

---

## Почему два слоя, а не один

Каждый слой закрывает слепое пятно другого:
- Nginx не знает про email — видит только IP
- Dragonfly не защищает от флуда — запрос уже дошёл до JVM до проверки лимита

Вместе дают полную защиту без избыточной сложности.

## Почему Nginx реализован первым

Dragonfly-лимиты требуют реализации в коде приложения: дизайн, тестирование, единый стандарт обработки ошибок. Nginx даёт edge-защиту без единой строки кода — разумный первый шаг, пока Dragonfly-слой готовится.

---

## Последствия

- Nginx добавлен в `docker-compose.yaml` и Helm (`values-prod.yaml`): `limit-rps: 20`, `limit-burst-multiplier: 5`
- Порт приложения не открыт наружу, весь внешний трафик идёт через nginx
- **Запланировано:** per-email лимиты через Dragonfly

| Ключ | TTL | Лимит |
|---|---|---|
| `rl:login:{email}` | 15 мин | 5 попыток |
| `rl:register:{ip}` | 1 час | 10 регистраций |
| `rl:reset:{email}` | 1 час | 3 запроса |
