# ADR-002: Выбор транспортного протокола

**Статус:** Принято  
**Дата:** 2026-03-15  
**Контекст:** Engineer Challenge — модуль аутентификации, Kotlin/JVM (ADR-001)

---

## Контекст и постановка проблемы

Auth Service реализует три операции: регистрация, авторизация, восстановление пароля.
Основной клиент — браузерное SPA (desktop-first).
API Gateway не входит в scope текущего этапа: клиент взаимодействует с Auth Service напрямую.

Каждая операция имеет несколько явных error cases с разной семантикой:
`WeakPasswordError`, `EmailAlreadyTaken`, `AccountLocked`, `InvalidCredentials`.
Рассинхронизация контракта ошибок — структурное свойство домена:
некорректная обработка error case на клиенте ведёт к потере конверсии,
security-рискам или production-инциденту.

---

## Критерии выбора

1. **Управление контрактом ошибок** — насколько протокол делает некорректную обработку error cases сложной, а правильную — очевидной
2. **Совместимость с браузером** — без дополнительной инфраструктуры
3. **Защита auth-флоу** — возможности rate limiting и abuse protection
4. **Операбельность** — стоимость эксплуатации и диагностики

---

## Рассмотренные варианты

### Вариант A: REST

Стандартный `fetch()` без SDK. Каждый endpoint — отдельная метрика и строка в access-log.
Rate limiting по URL-пути — стандартными инструментами прокси без кастомного кода.

**Управление контрактом ошибок:** REST не типизирует error cases на уровне протокола.
При schema-first OpenAPI + кодогенерации клиентских типов расхождение ловится на этапе сборки.
Без кодогенерации — неформальный договор, который расходится с кодом.

**Вердикт:** Сильный вариант с предсказуемой операционной стоимостью.
Ключевой недостаток: контракт ошибок управляется процессом, не инструментом.

---

### Вариант B: gRPC

gRPC несовместим с браузерным клиентом напрямую: HTTP/2 Trailers недоступны из JavaScript.
Любой вариант решения (grpc-web, grpc-gateway, BFF) требует дополнительного инфраструктурного компонента.
На текущем этапе этот компонент не имеет бизнес-обоснования.

**Вердикт:** Отклонён. Пересматривается при появлении межсервисной коммуникации.

---

### Вариант C: GraphQL (выбран)

Работает поверх стандартного HTTP + JSON — нативная поддержка в браузерах без дополнительной инфраструктуры.

**Управление контрактом ошибок:** union error types в SDL переносят ответственность
за корректную обработку error cases с разработчика клиента на компилятор.
Клиент не может проигнорировать `AccountLocked` или перепутать его с `InvalidCredentials` —
это ошибка компиляции, не production-инцидент.

Работает только при schema-first подходе: SDL — primary artifact в репозитории,
кодогенерация клиентских типов — обязательный шаг CI, code-first запрещён.

Пример схемы:

```graphql
mutation RegisterUser(input: RegisterUserInput!): RegisterUserResult!

union RegisterUserResult =
  | RegisterUserSuccess
  | EmailAlreadyTakenError
  | WeakPasswordError
```

**Принятая стоимость:**

Единый `POST /graphql` исключает нативный rate limiting по URL — требует отдельного решения (TBD).
HTTP 200 на ошибки GraphQL требует настройки метрик для корректной observability.

**Вердикт:** Выигрывает по управлению контрактом ошибок. Дополнительная сложность принята явно.

---

## Матрица сравнения

| Критерий | REST | GraphQL | gRPC |
|---|---|---|---|
| Браузер без инфраструктуры | ✅ | ✅ | ❌ |
| Контроль контракта ошибок | ⚠️ Процессный (OpenAPI) | ✅ Инструментальный (компилятор) | ✅ Инструментальный (proto) |
| Rate limiting из коробки | ✅ По URL | ❌ Единый эндпоинт | — |
| Observability из коробки | ✅ Полная | ⚠️ Требует настройки | — |

---

## Решение

**Выбран GraphQL (schema-first).**

1. gRPC отклонён: требует инфраструктурного компонента без бизнес-обоснования.
2. Auth Service структурно чувствителен к рассинхронизации контракта ошибок. GraphQL управляет этим инструментально.
3. Дополнительная сложность защиты и observability принята явно. Митигации известны, стоимость конечна.
