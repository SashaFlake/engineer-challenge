# ADR: Выбор транспортного протокола для Auth Service

**Статус:** Принято
**Дата:** 2026-03-15
**Авторы:** SashaFlake

---

## Контекст

Auth Service реализует три операции: регистрация, авторизация, восстановление пароля.
Основной клиент — браузерное SPA (desktop-first).
API Gateway не входит в scope текущего этапа: клиент взаимодействует с Auth Service напрямую.

Каждая операция имеет несколько явных error cases с разной семантикой:
`WeakPasswordError`, `EmailAlreadyTaken`, `AccountLocked`, `InvalidCredentials`.
Рассинхронизация контракта ошибок — структурное свойство домена:
некорректная обработка error case на клиенте ведёт к потере конверсии,
security-рискам или production-инциденту.

---

## Критерии выбора

1. **Управление контрактом ошибок** — насколько протокол делает некорректную обработку error cases сложной, а правильную — очевидной
2. **Совместимость с браузером** — без дополнительной инфраструктуры
3. **Защита auth-флоу** — rate limiting, abuse protection, информационная гигиена ответов
4. **Операбельность** — стоимость эксплуатации и диагностики

---

## Рассмотренные варианты

### Вариант A: REST

Стандартный `fetch()` без SDK. Каждый endpoint — отдельная метрика и строка в access-log.
Rate limiting по URL-пути, WAF-интеграция — стандартными инструментами прокси без кастомного кода.

**Управление контрактом ошибок:** REST не типизирует error cases на уровне протокола.
При schema-first OpenAPI + кодогенерации клиентских типов расхождение ловится на этапе сборки.
Без кодогенерации — неформальный договор, который расходится с кодом.
Принципиальное отличие от GraphQL: протокол не делает необработанный error case ошибкой компиляции —
это остаётся ответственностью разработчика клиента.

**Вердикт:** Сильный вариант с предсказуемой операционной стоимостью.
Ключевой недостаток: контракт ошибок управляется процессом, не инструментом.

---

### Вариант B: gRPC

gRPC несовместим с браузерным клиентом напрямую: HTTP/2 Trailers недоступны из JavaScript.
Любой вариант решения (grpc-web, grpc-gateway, BFF) требует дополнительного инфраструктурного компонента.
На текущем этапе этот компонент не имеет бизнес-обоснования помимо решения проблемы выбора протокола.

**Вердикт:** Отклонён. Пересматривается при наступлении триггера эволюции.

---

### Вариант C: GraphQL

Работает поверх стандартного HTTP + JSON — нативная поддержка в браузерах без дополнительной инфраструктуры.

**Управление контрактом ошибок:** union error types в SDL переносят ответственность
за корректную обработку error cases с разработчика клиента на компилятор.
Клиент не может проигнорировать `AccountLocked` или перепутать его с `InvalidCredentials` —
это ошибка компиляции, не production-инцидент.

Это работает только при schema-first подходе: SDL — primary artifact в репозитории,
кодогенерация клиентских типов — обязательный шаг CI, code-first запрещён.
Без этого аргумент про типобезопасность не работает.

Пример схемы:

```graphql
mutation RegisterUser(input: RegisterUserInput!): RegisterUserResult!

union RegisterUserResult =
  | RegisterUserSuccess
  | EmailAlreadyTakenError
  | WeakPasswordError
```

**Защита auth-флоу — принятая стоимость:**

Единый `POST /graphql` исключает нативный rate limiting по URL.
Полный периметр защиты требует:

| Проблема | Митигация | Сложность |
|---|---|---|
| Rate limiting по операции | Persisted Queries (PQL) + счётчик по `{ip, operationName}` | Высокая |
| PQL CI/CD интеграция | Генерация хешей при сборке клиента; публикация манифеста до деплоя; rollback-сценарии | Высокая |
| Observability (HTTP 200 на ошибки) | Operation name в метриках через OpenTelemetry | Средняя |
| DoS через сложные запросы | Query depth + complexity limiting | Средняя |
| Introspection в production | Отключить в конфиге | Низкая |

Один десинхронизированный деплой (клиент с новыми хешами, сервер со старым манифестом) —
HTTP 400 на все запросы в production.

**Вердикт:** Выигрывает по управлению контрактом ошибок.
Проигрывает по операбельности: PQL pipeline и OpenTelemetry увеличивают стоимость первоначальной настройки и эксплуатации.

---

## Матрица сравнения

| Критерий | REST | GraphQL | gRPC |
|---|---|---|---|
| Браузер без инфраструктуры | Да | Да | Нет |
| Контроль контракта ошибок | Процессный (OpenAPI + codegen) | Инструментальный (компилятор) | Инструментальный (proto) |
| Сложность защиты auth-флоу | Низкая | Высокая | — |
| Observability из коробки | Полная | Требует настройки | — |

---

## Решение

**Выбран GraphQL (schema-first).**

1. gRPC отклонён: требует инфраструктурного компонента без бизнес-обоснования на текущем этапе.
2. Auth Service структурно чувствителен к рассинхронизации контракта ошибок. GraphQL управляет этим инструментально — union error types + кодогенерация делают необработанный error case ошибкой компиляции. REST управляет тем же риском процессно — через OpenAPI и договорённости. Процессный контроль менее надёжен.
3. Дополнительная сложность защиты и observability GraphQL принята явно как стоимость инструментального контроля. Митигации известны, стоимость конечна.

---

## Последствия

**Положительные:**

- Некорректная обработка error cases — ошибка компиляции клиента, не production-инцидент
- SDL — верифицируемый живой контракт при schema-first + кодогенерации
- Браузерный клиент работает без прокси; схема совместима с мобильным клиентом без изменения протокола
- Архитектура готова к BFF-паттерну при росте системы

**Отрицательные:**

- PQL pipeline — высокая сложность, первоочередная задача до production-деплоя
- OpenTelemetry — prerequisite, не опция: без него все ошибки выглядят как HTTP 200
- Поддержка PQL при каждом изменении операций — ongoing операционная стоимость

**Явные риски и митигации:**

| Риск | Последствие | Митигация |
|---|---|---|
| Десинхронизация PQL-манифеста при деплое | HTTP 400 на все запросы | Проверка синхронизации — обязательный шаг CI перед деплоем frontend |
| Code-first drift | Контракт расходится с кодом | SDL — обязательный артефакт пайплайна; code-first запрещён |

---

## Эволюция

**Триггер пересмотра:** появление второго backend-сервиса с межсервисной коммуникацией или введение API Gateway.

При наступлении триггера вводится BFF/Gateway: GraphQL остаётся на его уровне или заменяется gRPC Gateway; внутренние сервисы переходят на gRPC.

До наступления триггера пересмотр не производится.
