# ADR-003: Выбор фреймворка

**Статус:** Принято  
**Дата:** 2026-03-14  
**Контекст:** Engineer Challenge — модуль аутентификации, Kotlin/JVM (ADR-001)

---

## Решение

**Ktor + Koin**

---

## Контекст и постановка проблемы

Язык выбран — Kotlin (ADR-001). Следующий выбор: фреймворк для HTTP-сервера и DI.

Стек сервиса сознательно минимален: один эндпоинт, три операции, одна СУБД. Нет Kafka, нет нескольких БД, нет межсервисных протоколов. Фреймворк должен соответствовать этому масштабу.

---

## Рассмотренные варианты

### Spring Boot (отклонён)

Spring Boot — широкий продакшн-стандарт с огромным сообществом. Его главная ценность — стартеры: готовые интеграции с Kafka, разными БД, кэшами, внешними сервисами. Чем больше интеграций — тем выше ROI автоконфигурации.

**Причина отклонения:** у нас нет ни одной из задач, для которых стартеры дают выигрыш. Для сервиса с минимальным стеком его автоконфигурация — не помощь, а лишний шум: подтягивается то, что не понадобится; аннотации проникают в доменные объекты, скрывая зависимости.

---

### Ktor + Koin (выбран)

Lightweight Kotlin-first фреймворк. Подключается только то, что явно задекларировано.

**Плюсы:**
- **Минимальный футпринт** — никаких автоматически подтягиваемых зависимостей; в стеке ровно то, что нужно
- **Прозрачность зависимостей** — Koin DSL: DI-граф читается как код, без рефлексии и неявных прокси; что зарегистрировано — видно статически
- **Асинхронность из коробки** — весь I/O через coroutines со structured concurrency, никакой дополнительной настройки
- **Kotlin-native API** — DSL-роутинг, extension functions; не Java-фреймворк с Kotlin-обёрткой
- **Изоляция домена** — фреймворк не диктует структуру приложения; доменная модель не содержит аннотаций фреймворка

**Минусы:**
- Меньше готовых решений — JWT, хэширование паролей реализуем явно
- Меньше сообщество и готовых примеров по сравнению со Spring Boot

---

## Обоснование выбора

Spring Boot — правильный выбор для системы с большим количеством интеграций. Там автоконфигурация даёт реальный выигрыш.

У нас другая задача: сервис с минимальным стеком, где каждая зависимость должна быть обоснована. Когда нечего автоматически конфигурировать — автоконфигурация становится шумом. Ktor соответствует этому масштабу: в стеке ровно то, что задекларировано, Koin-граф читается как код, никакой магии.

---

## Сравнение

| Критерий | Ktor + Koin | Spring Boot |
|---|---|---|
| Соответствие масштабу сервиса | ✅ минимальный стек | ⚠️ избыточный для одного эндпоинта |
| Прозрачность зависимостей | ✅ Koin DSL, статически | ❌ автоконфигурация + рефлексия |
| Асинхронность | ✅ корутины из коробки | ⚠️ WebFlux опционально |
| Изоляция домена от фреймворка | ✅ | ⚠️ аннотации проникают в модель |
| Автоматические интеграции | ❌ нет стартеров | ✅ Kafka, БД, кэш — одна зависимость |
| Kotlin-native API | ✅ | ⚠️ адаптация Java |

---

## Последствия

- HTTP-сервер: **Ktor** с Netty-движком
- DI: **Koin** — DSL, без рефлексии
- JWT и хэширование паролей реализуются явно в домене — TBD
- **Триггер пересмотра:** рост стека — Kafka, несколько БД, межсервисное взаимодействие → пересмотр в пользу Spring Boot
