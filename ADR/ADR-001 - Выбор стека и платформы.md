# ADR-001: Выбор языка и платформы

**Статус:** Принято  
**Дата:** 2026-03-14  
**Контекст:** Engineer Challenge — модуль аутентификации (регистрация, авторизация, восстановление пароля)

---

## Решение

**Kotlin + JVM**

---

## Контекст и постановка проблемы

Необходимо реализовать архитектурно-зрелый модуль аутентификации с явным DDD, CQRS и IaC.  
Задача оценивает не скорость сборки, а качество инженерного мышления и обоснованность trade-offs.

Рассматривались три варианта: **Kotlin/JVM**, **Python**, **Go**.

---

## Рассмотренные варианты

### Kotlin/JVM (выбран)

**Плюсы:**
- **Доступность:** разработчик обладает экспертной квалификацией в Kotlin → ниже когнитивная нагрузка → фокус на архитектуре, а не на борьбе с языком
- **Выразительность для DDD:** `sealed class` для команд/событий/ошибок, `data class` для Value Objects, `value class` для обёрток примитивов — доменная модель читается как спецификация
- **ФП из коробки:** `Either<DomainError, T>`, явный контроль сайд-эффектов, функциональные цепочки без instanceof-проверок
- **Асинхронность:** корутины со structured concurrency — явный контекст, отмена, таймауты без callback hell
- **Поддерживаемость:** строгая типизация, null safety, зрелая экосистема, большое сообщество — низкий риск нераскрытых проблем в долгосрочной перспективе
- **Перформанс:** JVM с JIT-компиляцией — высокий throughput под нагрузкой; широкие возможности тюнинга GC

**Минусы:**
- Высокое потребление RAM по сравнению с Go/Python
- Долгий холодный старт JVM — некритичен при текущих требованиях

---

### Python ❌ (отклонён)

**Плюсы:**
- Быстрый старт, низкие затраты на инстанс, хорошие возможности асинхронности

**Причины отклонения:**
- Отсутствие полноценной многопоточности
- Более слабая система типов усложняет моделирование доменных инвариантов
- Квалификация ниже, чем в Kotlin → выше риск архитектурных ошибок именно там, где задача требует максимальной аккуратности
- Меньше устоявшихся паттернов для DDD/CQRS в экосистеме

---

### Go ❌ (отклонён)

**Плюсы:**
- Быстрый запуск, минимальное потребление ресурсов, сильная статическая типизация

**Причины отклонения:**
- Нет опыта разработки на Go → высокий риск непредвиденных проблем в ходе реализации
- Минималистичная система типов затрудняет выразительное DDD-моделирование
- Отсутствие устоявшихся паттернов для CQRS/DDD в экосистеме

## Сравнительная таблица

| Критерий | Kotlin/JVM | Python | Go |
|---|---|---|---|
| Выразительность для DDD | ✅ Нативная | ⚠️ Возможна | ⚠️ Минималистична |
| ФП-возможности | ✅ Полные | ⚠️ Частичная | ❌ Минимальные |
| Асинхронность | ✅ Корутины | ✅ asyncio | ✅ Горутины |
| Перформанс под нагрузкой | ✅ JIT/GC тюнинг | ⚠️ GIL | ✅ Высокий |
| Холодный старт | ❌ Медленный | ✅ Быстрый | ✅ Мгновенный |
| RAM | ❌ Высокое | ✅ Низкое | ✅ Очень низкое |
| Квалификация автора | ✅ Экспертная | ⚠️ Средняя | ❌ Нет опыта |
| Поддерживаемость / экосистема | ✅ Зрелая | ✅ Зрелая | ✅ Растущая |

---

## Последствия

- Используем FP-like подход для моделирования доменных ошибок
- Все I/O-операции — через корутины
- Холодный старт JVM — некритичен при текущих требованиях
- Выбор фреймворка, транспорта, СУБД — TBD в следующих ADR
