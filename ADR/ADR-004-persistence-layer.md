# ADR-004: Выбор СУБД

**Статус:** Принято  
**Дата:** 2026-04-04  
**Контекст:** Engineer Challenge — модуль аутентификации, деплой в Kubernetes (ADR-001, ADR-003)

---

## Решение

**Dragonfly** — Redis-совместимое KV-хранилище

---

## Контекст и постановка проблемы

Приложение деплоится в Kubernetes с двумя репликами. Изначально все репозитории использовали `InMemoryRepository` на основе `ConcurrentHashMap`. При горизонтальном масштабировании это приводит к split-brain: пользователь, зарегистрированный на pod-1, недоступен на pod-2.

Требуется shared state между подами. Домен прост: две сущности (`User`, `PasswordResetToken`), без сложных связей и агрегаций.

Рассматривались три класса хранилищ: **KV** (Dragonfly), **SQL** (PostgreSQL), **Document NoSQL** (MongoDB).

---

## Рассмотренные варианты

### Dragonfly (выбран)

Redis-совместимое KV-хранилище с многопоточной архитектурой.

**Плюсы:**
- **Простота инфраструктуры** — нет PersistentVolume / PVC; stateless deployment в Kubernetes
- **Один компонент закрывает оба use case:** персистентность пользователей (HASH) и TTL-токены (STRING + EXPIRE)
- **Нативный TTL** — `PasswordResetToken` истекает автоматически без cron
- **Лёгкий переезд** — благодаря архитектуре с портами и адаптерами (ADR-001) замена СУБД требует только нового адаптера репозитория; доменная модель не меняется
- Совместим с Lettuce-клиентом без изменений кода

**Минусы:**
- `findByEmail` требует вторичного индекса вручную (`user:email:{email} → uuid`) — нет нативных запросов по полям
- Атомарность HSET + SET индекса требует MULTI/EXEC
- Персистентность по умолчанию отсутствует — требует `--save` или AOF

---

### PostgreSQL (отклонён)

**Плюсы:**
- `findByEmail` — простой `WHERE email = ?` с индексом
- Полные ACID-гарантии, надёжная персистентность

**Причины отклонения:**
- Требует PersistentVolume + PVC — StatefulSet усложняет деплой
- TTL для `PasswordResetToken` требует cron или фоновой задачи
- Избыточен для домена без сложных связей и агрегаций

---

### MongoDB (отклонёна)

**Плюсы:**
- `findByEmail` — нативный запрос с индексом
- TTL index — автоудаление токенов
- Гибкая схема

**Причины отклонения:**
- Требует PersistentVolume + PVC — противоречит цели минимизации компонентов
- TTL index не мгновенный: фоновый процесс раз в 60 секунд
- Гибкая схема не даёт преимуществ при фиксированной структуре `User`

---

## Сравнение

| Критерий | Dragonfly | PostgreSQL | MongoDB |
|---|---|---|---|
| PVC / StatefulSet | ❌ Не нужен | ✅ Нужен | ✅ Нужен |
| Нативный TTL | ✅ Мгновенный | ❌ Cron | ⚠️ ~60 сек |
| Запросы по полям | ❌ Вручную | ✅ SQL | ✅ Нативно |
| ACID | ⚠️ MULTI/EXEC | ✅ Полный | ✅ С 4.0 |
| Сложность для домена | ✅ Соответствует | ⚠️ Избыточен | ⚠️ Избыточен |

---

## Схема ключей

| Ключ | Тип | Содержимое | TTL |
|---|---|---|---|
| `user:{uuid}` | HASH | все поля `User` | нет |
| `user:email:{email}` | STRING | uuid | нет |
| `reset:{token}` | STRING | `userId\|expiresAt` | да |
| `user-token:{userId}` | STRING | token | да |

---

## Последствия

- `InMemoryRepository` сохраняется для локальной разработки без Docker (`STORAGE_BACKEND=memory`)
- Переключение через `STORAGE_BACKEND` — без изменения кода
- В production — включить Dragonfly `--save` или AOF
- При усложнении домена (JOIN, агрегации) — PostgreSQL как направление эволюции
