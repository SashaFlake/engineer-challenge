# ADR-002: Выбор фреймворка

**Статус:** Принято  
**Дата:** 2026-03-14  
**Контекст:** Engineer Challenge — модуль аутентификации, Kotlin/JVM (ADR-001)

---

## Решение

**Ktor + Koin**

---

## Контекст и постановка проблемы

Язык выбран — Kotlin (ADR-001). Следующий выбор: фреймворк для HTTP-сервера и DI.

Стек сервиса сознательно минимален: один GraphQL-эндпоинт, три операции, Dragonfly, Postgres. Нет Kafka, нет нескольких БД, нет межсервисных протоколов. Фреймворк должен соответствовать этому масштабу.

---

## Рассмотренные варианты

### Spring Boot (отклонён)

Spring Boot — широкий продакшн-стандарт с огромным сообществом. Его главная ценность — стартеры: готовые интеграции с Kafka, разными БД, кэшами, внешними сервисами. Чем больше интеграций — тем выше ROI автоконфигурации.

**Причина отклонения:** у нас нет ни одной из задач, для которых стартеры дают выигрыш. Spring Boot спроектирован для систем, где много что нужно подключить и настроить. Для сервиса с чётким минимальным стеком его автоконфигурация — не помощь, а лишний шум: подтягивается то, что не понадобится; аннотации проникают в доменные объекты.

---

### Ktor + Koin (выбран)

Lightweight Kotlin-first фреймворк. Подключается только то, что явно задекларировано.

**Плюсы:**
- **Минимальный футпринт** — никаких автоматически подтягиваемых зависимостей; в стеке ровно то, что нужно
- **Явное управление зависимостями** — Koin DSL: DI-граф читается как код, без рефлексии и неявных прокси; что зарегистрировано — видно в compile time
- **Корутины** — весь I/O асинхронный через structured concurrency, без настройки
- **Kotlin-native API** — DSL-роутинг, extension functions; не Java-фреймворк с Kotlin-обёрткой
- **Изоляция домена** — фреймворк не проникает в доменные объекты; домен, порты, инфра — сами

**Минусы:**
- Меньше готовых решений — JWT, хэширование паролей реализуем явно, без Spring Security
- Меньше сообщество и готовых примеров по сравнению со Spring Boot

---

## Обоснование выбора

Spring Boot — правильный выбор для системы с большим количеством интеграций: Kafka, несколько БД, внешние сервисы. Там автоконфигурация и стартеры дают реальный выигрыш — очень многое настраивается автоматически.

У нас другая задача: сервис с минимальным стеком, где каждая зависимость должна быть обоснована. Когда нечего подключать — автоконфигурация становится лишним шумом, а не помощью. Ktor соответствует этому масштабу: в стеке ровно то, что задекларировано, Koin-граф читается как код, никакой автомагии.

Если в будущем стек вырастет — Kafka, несколько БД, межсервисное взаимодействие — это будет триггером пересмотра в пользу Spring Boot.

---

## Сравнение

| Критерий | Ktor + Koin | Spring Boot |
|---|---|---|
| Соответствие масштабу сервиса | ✅ минимальный стек | ⚠️ избыточный для одного эндпоинта |
| Явное управление зависимостями | ✅ Koin DSL | ❌ автоконфигурация + рефлексия |
| Автоматические интеграции | ❌ нет стартеров | ✅ Kafka, БД, кэш — одна зависимость |
| Kotlin-native API | ✅ | ⚠️ адаптация Java |

---

## Последствия

- HTTP-сервер: **Ktor** с Netty-движком
- DI: **Koin** — DSL, без рефлексии
- GraphQL: **graphql-kotlin** (schema-first, ADR-transport)
- **Триггер пересмотра:** рост стека — Kafka, несколько БД, межсервисное взаимодействие
